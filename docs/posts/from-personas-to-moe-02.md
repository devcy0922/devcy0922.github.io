# 내 히스토리를 데이터셋으로 바꾸는 일은 생각보다 어려웠다

내 글투를 모델에 넣고 싶어서 처음에는 자료를 많이 모으면 된다고 생각했다.

커밋, PR, Jira, Confluence, Slack을 모아 JSONL로 만들고, prompt와 completion을 나누면 학습 데이터가 될 것 같았다.

곧 알게 됐다.

내 히스토리는 데이터셋이 아니라 **서로 다른 계약을 가진 기록들의 모음**이었다.

## 같은 사람이 썼어도 정답의 모양이 달랐다

커밋은 변경 결과를 짧게 남긴다. PR은 변경을 검토할 사람을 위해 배경과 범위와 검증 결과를 설명한다. Jira는 문제와 영향과 상태를 추적한다. Confluence는 시간이 지나도 읽힐 설명을 남긴다.

Slack은 더 복잡했다. DM인지 팀 채널인지 전역 채널인지에 따라 허용되는 생략과 맥락이 달랐다. 상사, 동료, 후배, 외부 협업자에게 같은 문장을 보내면 안 되는 경우도 있다.

그래서 `style` 하나로는 부족했다.

```text
source       무엇에서 나온 기록인가
audience     누가 읽는가
relationship 어떤 관계인가
intent       무엇을 하려는가
format       결과는 어떤 구조인가
visibility   어디까지 공개되는가
```

이 라벨들은 모델을 예쁘게 개인화하기 위한 태그가 아니었다. 잘못된 채널에 잘못된 형식의 답변을 내보내지 않기 위한 입력 경계였다.

## 원문을 그대로 넣으면 안 되는 이유

기록에는 기술 내용 외에도 사람과 프로젝트와 조직에 대한 정보가 섞여 있었다.

공개 글에서 원문을 재현하는 것도 적절하지 않고, 학습 데이터로 쓸 때도 원문 보존이 항상 좋은 선택은 아니다. 그래서 수집과 학습 사이에 별도 정제 단계를 뒀다.

```text
수집
  → 중복 제거
  → 민감 정보 마스킹
  → 문맥 단위 분리
  → 구조 라벨링
  → 사람 검수
  → 학습/평가 분리
```

특히 Slack은 메시지 한 줄만 떼면 의미가 사라지기 쉬웠다. 앞의 질문, 뒤의 결정, 누가 답을 기다리는지가 같이 있어야 했다. 반대로 문맥을 너무 많이 붙이면 다른 대화의 정보가 섞였다.

데이터를 많이 보존하는 것과 필요한 문맥만 보존하는 것은 다른 문제였다.

## 5천 개 골든셋을 만들기로 했다

어느 순간부터 학습 loss만으로는 진전이 보이지 않았다.

모델이 내 말투를 닮았는지는 숫자 하나로 판단하기 어려웠다. 형식은 맞지만 사실이 틀릴 수 있고, 자연스럽지만 수신자에 맞지 않을 수 있다. Jira 템플릿을 잘 채워도 실제로는 다음 액션이 빠질 수 있다.

그래서 5천 개 규모의 골든셋을 만들기로 했다.

각 샘플에 단순히 정답 문장만 넣지 않고 다음을 함께 기록했다.

```text
expected_format
audience_fit
factuality
privacy_boundary
actionability
style_match
```

이 작업은 모델 학습보다 오래 걸렸다. 무엇이 좋은 답인지 먼저 정의해야 했기 때문이다.

“내가 쓴 것처럼 보이는가”는 주관적이지만, “필수 제목이 있는가”, “수신자에게 공개하면 안 되는 내용이 없는가”, “근거 없는 단정이 없는가”는 비교적 검증 가능한 조건으로 바꿀 수 있었다.

## 자동 라벨링을 했다가 다시 손으로 돌아갔다

5천 개를 전부 손으로 라벨링하는 건 부담스러웠다. 작은 모델과 규칙을 섞어 자동 라벨러를 만들었다.

처음에는 속도가 크게 올라갔다. 문제는 라벨러가 틀리는 방식이 일정하지 않았다는 점이다.

- PR을 Jira처럼 분류함
- 팀 채널과 전역 채널의 경계를 놓침
- 질문과 결정사항을 같은 intent로 표시함
- 짧은 메시지의 관계 맥락을 과하게 추정함

자동화 결과를 그대로 믿으면 학습 데이터가 조용히 오염됐다. 틀린 문장 하나보다 틀린 라벨 수천 개가 더 무서웠다.

결국 다시 손으로 일부를 고쳤다. 그리고 자동화와 수동 검수를 섞는 방식으로 바꿨다.

```text
자동화: 후보 라벨과 이상 징후 제시
사람: 경계가 애매한 샘플 판정
자동화: 일관성 검사와 중복 검사
사람: 골든셋 최종 승인
```

자동화의 역할은 사람을 완전히 빼는 것이 아니라, 사람이 판단해야 할 샘플을 줄이고 틀린 부분을 잘 보이게 만드는 쪽이 더 맞았다.

## 데이터셋도 코드처럼 버전이 필요했다

라벨을 수정하면 학습 결과가 달라졌다. 그런데 원본과 라벨과 split 기준이 함께 버전 관리되지 않으면 어떤 모델이 어떤 데이터로 만들어졌는지 설명할 수 없었다.

그래서 최소한 다음은 같이 저장했다.

```text
dataset version
label schema version
train/eval split seed
redaction policy version
labeler version
review status
```

이 과정을 거치면서 LoRA 학습보다 데이터 계약이 먼저라는 걸 배웠다.

모델이 이상한 답을 냈을 때 base model 탓인지, adapter 탓인지, 잘못된 라벨 탓인지 구분할 수 있어야 한다. 그 구분이 안 되면 하이퍼파라미터를 만지는 것부터 미신이 된다.

내 히스토리를 모델에 넣는 일은 결국 말투 복사가 아니었다.

어떤 기록을 어떤 목적과 공개 범위로 변환할지 정하는 데이터 설계 작업이었다.
